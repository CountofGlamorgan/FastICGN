# CLI output integrity and resume

Multi-frame output directories now carry a hidden `.opencorr-state/` ledger.
CSV columns, formatting, raw 36-byte records, and solver behavior are unchanged.
Two CLI flags select policy, never numbers: `--durability rename|fsync` and
`--repair`. `--verify-only <output_dir>` audits a directory without running
anything. Use a fresh, dedicated output directory for a new job.

## Publication and failures

Each CSV, raw frame, diagnostics CSV, and manifest is written to a uniquely
created temporary file in its destination directory. Short writes are handled;
write, fsync, close, publication, and directory-fsync failures cause a nonzero exit.
A multi-frame payload is published without replacing an existing destination.
Metadata is atomically replaced. A per-file intent precedes the payload;
a run-complete record is published only after all writers and manifests succeed.

## Durability policy

`--durability` selects only *when* data reaches the device. Both values use the
same temporary-file plus atomic `rename`/`link` publication, the same ledger, the
same intent-before-payload ordering, and the same rejection rules; every check is
digest-based, none depends on `fsync`.

| | `rename` (default) | `fsync` |
| --- | --- | --- |
| Partial file after `kill -9`, segfault, OOM | impossible | impossible |
| Partial file after power loss or kernel panic | possible, detected by digest on the next run | prevented |
| `fsync` per published frame | **0** | 4 (payload file, output directory, intent file, state directory) |
| Barrier per finished job | 1 pass over manifests, `contract.json`, both directories, and `complete.json` | the same, on top of the per-frame work |
| Diagnostics CSV | same policy, one more publication per frame | doubles the per-frame `fsync` count |

Crash consistency comes from `O_EXCL` + `link`/`rename`, not from `fsync`: the
page cache is shared by all processes, so a dead process can never expose a
half-written payload. `fsync` buys power-loss durability, which this
implementation does not otherwise certify (see *Scope and cost*). On this
hardware the four barriers cost about 10 ms per frame (800-frame runs on
2026-09-17, measured before the raw writer pipeline described below was
added; not re-timed since), so `rename` is the
default and `fsync` is the explicit opt-in for runs whose output must survive an
unplanned power cut without recomputation.

`--diagnostics` publishes a second file per frame through a bounded background
writer. Serialization and per-file fsync run on that worker; the main thread
can still wait for queue capacity or final drain. Both writers must finish
successfully before manifests and completion are published. The fsync policy
still performs roughly twice the file-publication barriers; this changes their
scheduling, not their durability semantics or the diagnostics CSV bytes.

The effective policy is printed as `Durability: <policy>` at run start and
recorded in the raw manifest, the diagnostics manifest and
`.opencorr-state/complete.json`. It is **not** part of the run contract: a job
started under one policy may be resumed, extended or verified under the other.

Under `rename`, a power loss can leave a published frame incomplete while its
ledger entry claims success. The next run detects this by digest and refuses;
`--repair` then regenerates exactly those frames.

## Repairing damaged output

Without `--repair`, any tracked frame that fails verification (truncated, same
length but different content, present without a valid intent, or a manifest
whose content does not parse) rejects the whole run and preserves every file;
the error names `--repair`.

With `--repair`, those files are moved to
`.opencorr-state/quarantine/<UTC timestamp>-<pid>/` and regenerated by the
ordinary replay from frame 1. Nothing is deleted, verified frames keep their
inode and modification time, and the run prints how many files were quarantined
and where. Crash residue is not part of this bargain: it is archived on every
resume, with or without `--repair`, as described under resume housekeeping below.

`--repair` does not relax the safety boundary. Changed inputs, parameters or
binary, reordered or shortened target lists, unknown files in the output or
diagnostics directory, outputs that are symlinks, a missing or foreign
`contract.json`, and pre-ledger
outputs with no run record are still rejected with or without it.

Atomicity is **per file**, not a transaction across every frame and manifest.
On failure, other queued frames may already have committed successfully. They
remain available for validation and recovery. A crash may leave private
`.opencorr-tmp-*` files; they are never mistaken for completed frames. Recognized
private names are archived after validation on resume (see housekeeping below).
Keep the ledger with the frame files.

The pipeline wrapper preserves frame directories and its target list when the
CLI fails, so a rejected or interrupted run does not erase the evidence. Normal
successful pipeline cleanup still follows `--keep-frames`.

Single-frame mode also uses checked, atomic per-file publication, while retaining
its existing overwrite behavior. It has no multi-frame ledger, lock, or resume
contract. A raw frame and its manifest are not one atomic transaction: always
check the command's exit status before consuming that pair.

## Repeating or extending a multi-frame command

Run the same command against the same output directory. Before computing, the
CLI checks:

- the exact executable content, build identity, and the CLI options that decide
  the output (listed under *What the contract compares* below);
- canonical reference/target paths and complete input content fingerprints;
- the target order and output names (identical list, or append to an identical prefix);
- expected rows/bytes and content fingerprints of existing payloads;
- strict JSON syntax and manifest layout, frame identities, and completion records.

Output names must be unique plain filenames, without directory traversal,
control characters, reserved state names, or collisions after `.bin` conversion.
Reference, target, output and diagnostics paths and output names must be valid
UTF-8; the ledger and manifests are JSON, so a non-UTF-8 path (for example a
GBK-encoded directory name) is rejected at startup with a `non-UTF-8 ...`
message, before any file is created.
The output and diagnostics directories reject unrelated files; the current
`--tar-list` control file is allowed. A nonblocking directory lock excludes
cooperating concurrent runs, including runs sharing a diagnostics directory.

A fully complete matching job returns after verification without recomputing or
rewriting its files. This is **not** an O(1) check: it re-reads and fingerprints
every output file and every input, and reports the file count and megabytes it
verified. An incomplete or extended job **replays from frame 1** to
restore both prior-result buffers and the initial bad-ratio baseline. Existing
frames are serialized again and compared against their recorded fingerprints;
the existing inode and modification time are preserved. Missing frames are
published only after this replay verifies their content. This is not a solver
checkpoint, and its compute cost can approach a fresh full run.

A matching intent with a missing payload is recoverable. An existing payload
with no intent, truncation, or same-size corruption is rejected and preserved;
rerun with `--repair` to quarantine and regenerate just those files, or move the
suspect run aside and use a fresh output directory to recompute.
Pre-ledger outputs are **not adopted automatically**. Changed inputs, parameters,
binary, reordered or shortened target lists are rejected. Rebuilding the same
commit can change the binary identity and therefore prevent resume.

### What the contract compares, and what a rejection says

`.opencorr-state/contract.json` records, and a resume compares:

- the executable: its content fingerprint, `git_hash` and `build_date`;
- the reference image: canonical path and content fingerprint;
- the options that decide the output bytes: `radius`, `step`, `dual_gpu`,
  `kernel`, `fftcc`, `max_iteration`, `convergence`, `skip_fftcc`,
  `poi_fallback`, `temporal_extrapolation`, `format`, `line_ys`, `input_depth`,
  `input_align`, `input_normalize`, `output_roi_enabled`, `output_roi`,
  `output_step`, `diagnostics`, `diagnostics_dir`;
- the target list: each input's canonical path and fingerprint, its output name
  and file. It may only grow, by appending.

Not compared, because they cannot change an output byte: `--durability`,
`--repair`, `--quiet`, and the four scheduling options `--gpu-device`,
`--threads`, `--preload`/`--no-preload` and `--decode-threads`. A job may be
resumed, extended or verified under other values of these; the raw manifest's
`engine` block records the values of the run that last wrote it. So the default
`--threads` (logical CPUs minus one, which follows `taskset`, a container's CPU
set or another machine) no longer decides whether a directory can be resumed,
and a mistyped `--gpu-device` no longer makes a directory unusable: the failed
attempt wrote a contract, and the corrected command matches it.

The scheduling options left the contract on 2026-10-05, after each of them was
varied against the frozen 60-frame production anchor protocol (`--threads` 1, 4,
10, 39 and the default; `--no-preload`; `--decode-threads` 2 and 8;
`--gpu-device` 0 and 1; two combinations) and every output tree hashed to the
recorded anchor. The CPU-only backend and `--fftcc cpu` were checked the same
way against their own baselines. A contract written before that still lists
`gpu_device`, `threads`, `preload` and `decode_threads`; those four keys are
ignored when such a contract is compared.

A rejection names what differs, with the recorded and the requested value:

```text
Error: resume rejected: run configuration/reference/binary changed (recorded -> requested): options.max_iteration: 10 -> 11; an option that decides the output differs from the recorded run; use a new output directory for a different run
Error: resume rejected: run configuration/reference/binary changed (recorded -> requested): binary.bytes: 1131312 -> 1362472; binary.digest: "450a..." -> "4774..."; build_date: "..." -> "..."; git_hash: "638ad1845d01" -> "0123456789ab"; another build of the executable wrote this directory (resume needs the byte-identical binary); use a new output directory for a different run
Error: resume rejected: targets changed/reordered; only an identical prefix plus append is allowed: target 3 of the recorded 60 differs (recorded -> requested): input.path: "/data/a/000003.tif" -> "/data/b/000003.tif"
Error: resume rejected: targets changed/reordered; only an identical prefix plus append is allowed: the recorded run lists 60 targets, this command only 20 (a shorter list is not a resume)
```

At most eight fields are listed, then a count of the rest. The first sentence of
each message is unchanged from earlier binaries, which printed nothing after it.
The same text is the `error` of the status line on stdout. A rejected resume
never changes the directory.

Extending a target list writes the longer contract to
`.opencorr-state/contract.pending.json` and promotes it to `contract.json` only
once the first appended payload has been published. An append that fails before
that point therefore still resumes with the **original, shorter** list. Once an
appended frame exists on disk the extended list is the only valid one, because
the shorter list would see that frame as an untracked file; delete the extra
`frame_*.bin` (and rerun with the short list) or keep using the long list.
A process that dies between publishing that first appended payload and promoting
the contract leaves exactly this state with `contract.json` still the shorter
one: rerun the append command with the long list as it was (no `--repair`).
`--verify-only` reports it as `incomplete` and names the frame under
`appended_published`.

Raw and diagnostics manifests retain their existing public layouts; provenance
and integrity records live in the hidden ledger. JSON uses a pinned parser with
UTF-8 and Unicode-escape support; duplicate keys, invalid grammar, excessive
nesting, and incompatible layouts are rejected. Whitespace/escape-only metadata
reformatting is accepted. Completed manifest semantics must remain unchanged.
Missing manifests can be regenerated by replay.

## Verifying a directory without running it

`opencorr_cli_cuda_mvp --verify-only <output_dir>` answers one question: is this
multi-frame output directory complete, and does every file still match the
ledger? It computes nothing, opens no GPU, and creates, moves, repairs or
rewrites nothing: no quarantine, no archiving of leftovers, not one inode or
modification time changes (a read-only directory can be audited). It needs
neither the original command line nor the binary that wrote the directory.

It prints one JSON object on one line of stdout (and a one-line summary plus
each problem on stderr), and exits 0 only for `"status": "complete"`:

```json
{"schema":"fasticgn.verify-only/1","status":"complete","complete":true,"exit_code":0,"output_dir":"/data/run-01","frames_expected":60,"frames_verified":60,"files_expected":61,"files_verified":61,"bytes_verified":369446665,"rows_per_frame":171024,"problems":[],"warnings":[],"completion":{"durability":"rename","present":true,"state":"current"},"manifests":[{"file":"manifest.opencorr-raw.json","state":"ok"}],"inputs":{"changed":[],"changed_count":0,"checked":61,"missing":[],"missing_count":0,"status":"match"},"contract":{"...":"..."},"missing":[],"missing_count":0,"mismatched":[],"mismatched_count":0,"no_intent":[],"no_intent_count":0,"invalid_intent":[],"invalid_intent_count":0,"untracked_outputs":[],"untracked_outputs_count":0,"untracked":["tar_list.txt"],"untracked_count":1,"residue":[],"residue_count":0,"pending_append":false,"pending_append_state":"none","appended_published":[],"appended_published_count":0,"tool":"opencorr_cli_cuda_mvp","version":"1.2.0","git_hash":"0123456789ab"}
```

| `status` | Meaning | Exit |
| --- | --- | --- |
| `complete` | every promised file is present and matches its ledger record, `complete.json` belongs to this contract, the manifests match it | 0 |
| `incomplete` | nothing contradicts the ledger, but the run is not finished: payloads or a manifest are missing, `complete.json` is absent or belongs to another target list, or an append was cut off right after its first new output (`appended_published`, see step 5). Rerunning the command that was interrupted resumes it; for an append that is the command with the **longer** target list | 1 |
| `damaged` | something contradicts the ledger (see the lists below). Rerunning the interrupted command with `--repair` regenerates the tracked files named in `mismatched`, `no_intent` and `invalid_intent`; entries in `untracked_outputs` are not the run's and have to be moved away by hand | 1 |
| `inputs_changed` | the outputs are complete and match the ledger, but an input image no longer has the recorded content: the frames describe images that are no longer at those paths | 1 |
| `locked` | another process holds the directory lock (a run is in progress); verify again when it has finished | 1 |
| `not_a_run` | no `.opencorr-state/contract.json` (single-frame output and binaries older than the ledger write none), or not a directory | 1 |
| `not_found` | the path does not exist | 1 |
| `error` | the directory could not be read (`problems` names the I/O error), or the command line did not name exactly one directory (`output_dir` is then `null`) | 1 |

What it does, in the order a careful reader would otherwise have to do by hand:

1. **Contract.** Reads `.opencorr-state/contract.json` and derives the promised
   files from it: one payload per target, the diagnostics files and the
   manifests. `contract` in the report summarises the recorded run (`git_hash`,
   `build_date`, `binary_digest`, `reference`, `options`, the contract `digest`,
   and `legacy_scheduling_options`: which of the four scheduling keys an older
   binary still recorded).
2. **Payloads.** Each promised file must exist, be a regular file, and have the
   size and XXH3-128 digest of its ledger record; all frames must record the
   same row count. `missing` (the next run publishes them by replay),
   `mismatched` (truncated, altered, or not a regular file), `no_intent` (a file
   without a ledger record) and `invalid_intent` (a record that does not parse
   or describes another file) list up to 20 names each, with the exact total in
   `<name>_count`.
3. **Completion record.** `completion.state` is `current` when
   `complete.json` carries the digest of this contract, `other_contract` when it
   describes another target list (an append or resume was started and did not
   finish), `missing`, or `invalid`. `complete.json` alone never proved
   completeness: it is not withdrawn when a later resume, append or repair
   starts changing the directory.
4. **Manifests.** Each manifest must parse and, when the completion record is
   current, still have the digest that record took (`manifests[].state`: `ok`,
   `missing`, `invalid`, `changed`). For raw output the manifest's frame list
   must be exactly the contract's target list, with the byte counts of the files
   on disk, because readers take the frame list from the manifest.
5. **Leftovers and interrupted appends.** `residue` lists `.opencorr-tmp-*`
   temporaries, traces of an interrupted run that the next run archives; they
   are a warning and do not change the status. `pending_append` says whether
   `contract.pending.json` exists, and `pending_append_state` what it is:
   - `append`: it extends the recorded contract (same binary, reference and
     options, the recorded targets as a prefix, more targets after them). An
     append was started and has not replaced the recorded contract yet. Two
     cases follow from where it stopped:
     - no appended output is on disk: the earlier, shorter run is still
       complete and is reported as `complete`, with a warning. Either target
       list can be run next.
     - the first appended output is on disk (`appended_published`): the process
       died between publishing it and promoting the longer contract. Status
       `incomplete`. **Rerun the append command, with the longer target list,
       unchanged**; it continues and needs no `--repair`. The shorter list is
       no longer accepted (`untracked entry in output directory`), because it
       does not account for that output.
     An appended output is listed in `appended_published` only when a resume
     with the longer list would accept it: the pending contract promises the
     file, the file is a regular file, and its size and digest match its own
     ledger record. An appended output that is on disk and fails that test is
     filed under `mismatched`, `no_intent` or `invalid_intent` and the status is
     `damaged`; the longer list with `--repair` regenerates it.
   - `promoted`: it repeats the recorded contract. The append was promoted and
     only this file is left over (a warning).
   - `unrelated` or `unreadable`: it does not extend the recorded contract, or
     does not parse as a contract. It is ignored (a warning), so an output it
     might have explained is judged like any other entry under step 6.
   - `none`: there is no such file.
6. **Foreign entries.** `untracked_outputs` lists entries the ledger does not
   name that carry the extension of the outputs the run publishes in that
   directory: `.bin` or `.csv` next to the frames, `.csv` in the diagnostics
   directory. The entry's type does not matter: a regular file, a symlink
   (dangling or not) and a directory all count, because a reader that globs
   `frame_*` picks up any of them. Status `damaged`. `untracked` lists every
   other entry the ledger does not name. The run's own `--tar-list` file is
   usually one of them (the pipeline keeps `tar_list.txt` there), so this list
   is information only and does not change the status.
7. **Inputs.** The reference and every target image are fingerprinted again and
   compared with the contract: `inputs.status` is `match`, `changed`, or
   `missing` when images are no longer at the recorded paths (a warning; they
   could not be compared, and rerunning the command would need them there).

The audit holds a shared lock on the directory while it reads, so several audits
can run together. A run started during an audit is refused with `run directory
already locked` and can simply be started again. Verification reads every
payload and every input once, like the verified-complete path of a rerun
(measured on the lab host for 60 raw frames of 6 MB each plus their 61 input
images: 0.12 s from a warm page cache, 0.35 s on the first read).

**`complete` is a statement about the run's outputs, not a promise that the
original command will be accepted again.** A resume applies the ledger's own,
stricter rule and rejects every entry it does not know except its `--tar-list`
file: a directory that lists `notes.txt` or a subdirectory under `untracked` is
`complete` here, and the original command still fails with `untracked entry in
output directory` until those entries are moved away. Rerunning also needs the
byte-identical binary (see below), which `--verify-only` does not.

With no directory, an empty one or more than one argument, `--verify-only`
prints an `Error:` line on stderr and still one JSON object on stdout, with
`"status": "error"`, `"output_dir": null` and the reason in `problems`; exit 1.

`--verify-only` does not judge the measurement
([quality checks](quality-checks.md) do that) and has nothing to check in a
directory whose `.opencorr-state/` was removed. `pipeline/fasticgn_io.py`
`run_status()` is the lighter Python-side look: it has no XXH3 and therefore
does not compare content.

## Other binaries and existing directories

The executable's fingerprint is part of the contract. A directory can therefore
be resumed only by the byte-identical binary that wrote it: not by an older
build, not by a newer one, not by a rebuild of the same commit. That was always
so and is unchanged; what a newer binary adds is the reason in the message and
`--verify-only`, which works on directories written by any ledger-aware binary.
Measured on 2026-10-05 with 60-frame raw runs, each on its own copy:

| Binary | Directory written by | Result |
| --- | --- | --- |
| a binary with the ledger but without this change (two builds tried) | a newer binary, complete or interrupted | `resume rejected: run configuration/reference/binary changed`, exit 1, directory byte-for-byte unchanged, with or without `--repair` |
| a newer binary | an older ledger-aware binary, complete | rejected the same way, naming `binary.bytes`, `binary.digest`, `build_date` and `git_hash`, and not the four scheduling keys the older contract still lists; `--verify-only` reports `complete` |
| a binary older than the ledger (before 2026-09-17) | any binary, complete | every frame is "skip existing", exit 0, nothing changes |
| a binary older than the ledger | any binary, interrupted | **exit 0 and wrong output**: it skips the frames that exist, takes the first missing frame as a new skip-FFTCC baseline and computes the rest from there, so the frame tree differs from an uninterrupted run, and it rewrites the manifest. `--verify-only` afterwards reports `damaged` (in the test, interrupted after 29 of 60 frames: one payload that contradicts its ledger record and 30 without one) |

So: never point a binary older than the ledger at a directory that has an
`.opencorr-state/`, and do not expect any other binary to continue a run. To
continue after changing the binary, start a new output directory.

## Raw writer pipeline and cost counters

Raw output leaves the main loop through two single-threaded stages: a format
stage that serializes a published POI buffer into the 36-byte records, and a
publish stage that digests those bytes and performs the ledger and file
publication. The sustained writer cost is therefore the slower stage, not the
sum of both. Both queues are FIFO and each stage has one thread, so frames keep
submission order in the manifest, and the intent record still precedes its
payload for every frame. A frame that fails to serialize is never handed to the
publish stage.

Formatted payloads are pooled and bounded: up to eight are in flight between the
stages (about 47 MiB for a 171024-POI frame), which is where writer jitter is
absorbed, and a reused buffer costs neither an allocation nor a zero fill.

A multi-frame run reports the publication cost on stderr, accumulated over the
whole process: `publish resolve` (destination canonicalisation and the
serialized-size checks), `publish digest` (XXH3-128 over each payload),
`publish intent` (the ledger record), and `publish payload create` / `write` /
`link` for the payload file itself, with `Published payloads` as the count.
`Accumulated raw binary format` and `Accumulated raw binary write` remain the
per-stage totals. These are wall-clock sums inside each stage thread, so with
both stages running they overlap and do not add up to the run time.

## Scope and cost

This implementation is validated on Linux local filesystems. It requires POSIX
directory flock, atomic rename/hard-link publication, and directory fsync;
Windows and shared-filesystem durability/locking are not validated. Inputs must
remain immutable throughout a run. The checks do not provide snapshots against
concurrent external input edits, hardware-failure certification, or protection
against an owner deliberately rewriting files and their ledger together.

Runtime fingerprints use XXH3-128 to detect accidental corruption and mismatched
identities efficiently; they are **not cryptographic authentication**. The
scientific acceptance anchors remain SHA-256 over the original frame payloads.
Full input hashing, intent writes and (under `--durability fsync`) per-frame
barriers add I/O work, and fully completed-run verification also reads every
payload. Historical production timings do not apply automatically to this
candidate; measure the policy you intend to ship. See
[third-party sources](../third_party/README.md) and
[fault/recovery tests](../smoke/README.md).

## Resume housekeeping and completion repair

After input/configuration, payload, and manifest validation under the run and
diagnostics directory locks, every resume archives abandoned private files
matching `.opencorr-tmp-<digits>-<digits>` and `contract.pending.json` into the
run's quarantine directory. This also happens on the verified-complete fast
path. Files are moved aside, not deleted; frame payload inode/mtime is unchanged.
Keep the output directory dedicated to one job; non-cooperating external writers
are outside the lock contract. When anything is archived, the run prints one line
naming the quarantine directory and how many files were moved.

One classifier decides what the reserved `.opencorr-tmp-` namespace holds, and
both the resume scan and the post-run sweep use it, so `--repair` and a plain
resume see exactly the same names and treat them the same way. `--repair` only
widens what counts as repairable damage; it never widens residue archiving.
Housekeeping never fails a run: a reserved name whose remainder is not
`<digits>-<digits>`, and a well-formed reserved name that is not a regular file
(a directory, or a symlink), are both reported on stderr and left exactly where
they are, in either mode; neither is archived and neither rejects the run. Names
outside the reserved prefix remain `untracked entry` rejections. The second sweep
runs after the completion record is durable, so a failure there is reported as a
warning and still exits 0: a run whose completion is on disk always reports
success.

A completion record whose `contract_digest` is well formed (32 lowercase hex
digits) but is **not this run's** digest is not damage and is not repaired. It
is a completion statement about a different contract, so it carries no claim
about this one: the run ignores it, keeps every file, and continues as an
ordinary resume, replaying from frame 1 and re-verifying each existing payload
against its ledger entry. The output is byte-for-byte what a fresh run would
produce. Only a digest that is missing, not a string, or not 32 lowercase hex
digits is a damaged record.

`--repair` also handles malformed completion records and completion/manifest
mismatches: it quarantines the completion record, plus the single manifest a
verdict names when the completion and that manifest disagree, and replays the
verified run to rebuild them. Manifests that verified are left in place; the
replay rewrites them anyway, so a completion fault does not move healthy files.
The rejection reason is printed on stderr before anything is quarantined, and
only parse/schema/digest verdicts count as damage: `std::filesystem` errors and
other `std::system_error` I/O faults propagate as failures instead of being
repaired away. `readJson` draws the same line. A metadata file that is missing,
cannot be opened, or faults while being read raises `std::system_error` carrying
its `errno`; it is never isolated and never repaired, and the run exits 1 with a
message naming the path and the errno. A file that was read but does not parse,
does not match the schema, or carries the wrong digest stays a `runtime_error`
that `--repair` may quarantine. A directory or a symlink where a metadata file
belongs remains a hard rejection in either mode.
Input/configuration/binary changes still fail before this repair. Output
symlinks remain a hard error. A syntactically valid completion for an older
target prefix can be superseded by an append, as before. Quarantine is retained
for audit and is not a disk-space cleanup tool.
